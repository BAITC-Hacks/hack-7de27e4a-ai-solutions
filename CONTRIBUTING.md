# Как мы работаем в этом репозитории

## Ветки

```
main                              # всегда запускается и остаётся demo-safe
├── feat/alihan-intelligence      # A — Алихан
├── feat/manahnbet-digital-twin   # B — Манахнбет
└── feat/danik-hr-trust           # C — Даник
```

Все три ветки создаются из **одного** scaffold-коммита. Имена зафиксированы — вариант из
playbook (`feat/intelligence-engine` и т.п.) отменён, см. `docs/DECISIONS.md` #4.

## Коммиты

- префиксы `feat:`, `fix:`, `test:`, `docs:`, `chore:`;
- рабочий commit **не реже раза в 40 минут** — это защита от потери работы, а не формальность;
- перед merge прогнать свои тесты и `pnpm build`;
- сообщения по-английски, в императиве: `feat: add history replay for effective skills`.

## Merge

**Порядок: A → main, затем B → main, затем C → main.** После каждого merge — `pnpm test` и
`pnpm build` на main. Первый merge каждого потока — **не позже 02:20**.

Нельзя:

- просить Codex переписать весь репозиторий после начала параллельной работы;
- менять структуру `Recommendation` и других общих типов без сообщения двум другим;
- впервые мержить большую ветку после feature freeze;
- разрешать конфликт выбором `ours`/`theirs` без чтения контракта;
- добавлять новую библиотеку после 03:30 без критической необходимости.

## Общие типы

`src/lib/contracts/**` принадлежит потоку A и **заморожен после 00:20**. Порядок изменения:

```
сообщение в чат ДО правки -> правит владелец -> строка в docs/DECISIONS.md -> commit -> "сделайте pull"
```

## Integration handshake (02:20)

| Проверка | Ответственные | Pass condition |
|---|---|---|
| Import | A + B | UI создаёт тот же `NormalizedDataset`, что ожидает ядро |
| Recommendation | A + B | Реальный top-3 заменяет мок без переписывания UI |
| AI review | A + C | Allowlist ID и схема evidence совпадают |
| HR metrics | A + C | Агрегаты считаются из normalized store |
| Completion | все | Ledger меняет профиль, top-3 и HR на одном state |

## Данные

`data/source/` — стартовый набор организаторов. **Не редактировать.** Датасет синтетический,
но по условиям ТЗ за пределы хакатона не выносится: прежде чем коммитить его в публичный
репозиторий, уточнить у организаторов. Если решили не коммитить — добавить `data/source/` в
`.gitignore` и описать в README, куда его положить.

## Перед тем как открыть PR

- [ ] свои тесты зелёные (`pnpm test`)
- [ ] `pnpm build` проходит
- [ ] изменения только в своих каталогах
- [ ] общие типы не менялись (или менялись с уведомлением и записью в DECISIONS)
- [ ] нет hardcoded ID в продуктовом коде
- [ ] работает без `LLM_API_KEY`

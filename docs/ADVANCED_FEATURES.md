## 1. Агент для HR с инструментами

**Модель перестаёт быть редактором готового ответа и начинает сама добывать данные через наши функции.**

- Владелец: Даник / поток C
- Каталоги: `src/app/api/ai/**; src/lib/evaluation/**; src/components/trust/**; src/components/hr/**; tests/evaluation/**`
- Оценка: 1.5-2 часа

### Что это простыми словами

Сейчас всё работает так: мы сами посчитали рекомендацию, собрали факты и отдали модели готовый список. Модель только выбирает из него и склеивает предложения. Она ничего не решает и ничего не ищет.

Агент - это когда модель сама решает, какие данные ей нужны. HR пишет вопрос обычными словами: 'в каком отделе хуже всего с критичными навыками?'. Модель понимает, что ей нужны разрывы по отделам, запрашивает их у нас, смотрит результат, понимает, что нужно ещё покрытие активностями, запрашивает и его, и только потом отвечает. Несколько шагов вместо одного.

Ключевое: модель по-прежнему не видит базу. Она может только вызывать наши функции и получать наши числа. Выдумать сотрудника, уровень навыка или процент ей физически не из чего.

### Зачем это нужно

- Баллы. В критериях жюри в разделе технической реализации отдельной строкой стоит 'использование AI/agentic AI'. Это часть 25 баллов из 100. Сейчас у нас честный, но одношаговый вызов модели.
- Дашборд отвечает только на заранее зашитые вопросы. HR спросит своё - и упрётся в то, что мы не предусмотрели. Агент отвечает на любой вопрос, потому что сам собирает данные.
- Это же и защита от галлюцинаций: ответ агента проверяется по результатам вызванных инструментов. Любое число, которого нет в этих результатах, блокируется.
- И отдельно - честный аргумент на защите. Сейчас verifier требует, чтобы объяснение совпадало с нашим шаблоном символ в символ. Это максимально безопасно, но означает, что модель почти ничего не добавляет. Агент - способ дать AI настоящую работу, не потеряв контроль.

> Зона Даника, и это важно: 90% нужного уже написано им же. Агент - не новая подсистема, а один цикл вызовов и один новый режим проверки поверх готового.

### Что уже есть в репозитории

- src/app/api/ai/review/route.ts - готовый server route: проверка origin, лимит тела, Zod-валидация, ключ опционален
- src/app/api/ai/review/service.ts - полная лестница fallback: no_key / timeout / blocked / verified, замер latency
- src/app/api/ai/review/provider.ts - OpenAI-совместимый клиент: только https, temperature 0, json_object, в промпте прямо сказано, что входной JSON - недоверенные данные, а не инструкции
- src/lib/evaluation/verifier.ts - проверка ответа модели по белому списку
- src/lib/evaluation/explanations.ts - шаблоны фактов на ru/kk/en и функция, которая срезает из запроса всё, кроме идентификаторов и чисел
- Вывод: примерно 90% инфраструктуры готово. Отсутствует ровно одно - многошаговость и инструменты.

### Как сделать

**Шаг 1. Сделать инструменты (это просто обёртки над готовым кодом)**

- getGaps(employeeId) - поверх analyzeGaps из domain/recommendation
- getRecommendations(employeeId) - поверх recommendForEmployee
- findEmployees(role, grade, skillId, minLevel) - выборка по нормализованному датасету
- getSkillCoverage(skillId) - сколько людей ниже требования своего грейда
- getCatalogGaps() - навыки, для которых каталог не даёт прироста до требования
- simulate(employeeId, activityId) - поверх симулятора потока B
- Считать что-то новое не нужно: всё это в проекте уже написано и покрыто тестами

**Шаг 2. Описать инструменты схемой и отдать модели**

- Zod-схема на аргументы каждого инструмента, из неё же JSON Schema для tool-calling
- Аргументы валидируются ДО выполнения: неизвестный employeeId или skillId отклоняется сразу
- Результат инструмента - только идентификаторы и числа. Описания и заголовки из датасета не передаются: это недоверенный текст, ровно та же логика, что уже применена в provider.ts

**Шаг 3. Цикл вызовов**

- Вопрос -> модель просит инструмент -> выполняем -> отдаём результат -> повторяем
- Жёсткий предел: максимум 5 шагов и общий бюджет времени, иначе модель может ходить по кругу
- Каждому результату инструмента присваивается evidence id вида tool:3:getGaps
- Весь лог шагов сохраняется и возвращается клиенту

**Шаг 4. Проверка ответа - здесь единственное принципиально новое**

- Текущий verifier требует посимвольного совпадения с шаблоном. Для свободного ответа это не подходит
- Нужен второй режим проверки: извлечь из текста ответа все числа и все идентификаторы и убедиться, что каждое встречается в результатах вызванных инструментов
- Не прошло - ответ блокируется, показывается детерминированная сводка и причина блокировки
- Режим проверки выбирается явно: strict (существующий, для объяснения рекомендации) и grounded (новый, для агента)

**Шаг 5. Показать цепочку в интерфейсе**

- Панель 'как агент это посчитал': шаг 1 посмотрел разрывы, шаг 2 нашёл сотрудников, шаг 3 посчитал покрытие
- Каждый шаг разворачивается в фактический результат инструмента
- Это важнее, чем кажется: жюри должно увидеть, что агент реально работает, а не что мы так назвали обычный запрос

### Чего не делать

- Не передавать модели сырые профили, историю, имена и текстовые описания событий
- Не позволять модели менять ranking рекомендаций - это зона движка, агент только читает
- Не ломать существующий strict-режим: объяснение топ-3 продолжает работать как сейчас
- Не делать агента обязательным: без ключа HR-дашборд работает полностью, панель агента показывает 'отключено'

### Критерии приёмки

| Проверка | Ожидаемый результат |
|---|---|
| Вопрос требует данных из двух источников | Агент делает минимум 2 вызова инструментов и отвечает по ним |
| Модель называет сотрудника, которого нет | Ответ заблокирован, показана причина |
| Модель называет число, которого нет в результатах | Ответ заблокирован |
| Модель просит инструмент с несуществующим skillId | Аргументы отклонены до выполнения |
| Нет LLM_API_KEY | HR-дашборд работает полностью, панель агента отключена с понятным текстом |
| Модель зациклилась | Останов на 5 шаге, частичный результат с пометкой |
| В описании события лежит инъекция | Текст не попадает в инструменты вообще |

### Обязательные тесты

- агент выполняет многошаговый сценарий и возвращает лог шагов
- grounded-проверка блокирует число, отсутствующее в результатах инструментов
- grounded-проверка блокирует неизвестный идентификатор
- аргументы инструмента с несуществующим ID отклоняются до вызова
- превышение лимита шагов даёт корректный частичный ответ, а не ошибку
- без ключа возвращается статус no_key и дашборд не ломается
- strict-режим объяснения рекомендаций продолжает проходить прежние тесты

## 2. Подбор ментора вместо пустого ответа

**Если в каталоге нет курса, закрывающего разрыв, система предлагает не курс, а человека.**

- Владелец: свободный поток / новый модуль
- Каталоги: `src/domain/mentorship/**; точки показа согласовать с владельцами employee и hr; tests/mentorship/**`
- Оценка: около 1 часа

### Что это простыми словами

Сейчас, если после всех фильтров ни одна активность не подходит, сотрудник видит честное 'подходящих рекомендаций нет'. Честно - и бесполезно.

Идея простая: у компании уже есть люди с нужным уровнем навыка. Система находит их и предлагает как ментора. Развитие идёт не через каталог, а через коллегу.

### Зачем это нужно

- 17 сотрудников из 200 сейчас получают пустой ответ. Это измерено на реальном датасете, а не предположение.
- В каталоге всего 2 менторских события из 40. Этот способ развития почти не покрыт - дыра не у нас, а у каталога.
- Носители есть всегда: по всем 33 критичным навыкам в компании найдутся сотрудники уровня 4+. По SK_SYSTEM_DESIGN таких одиннадцать, и все - бэкендеры.
- Все остальные команды будут рекомендовать курсы. Рекомендовать человека не будет никто - это прямой вклад в критерий оригинальности.
- Для HR это ещё и ответ на вопрос 'что делать с навыками, которые каталог не закрывает': закрывать людьми, а не бюджетом.

> Это единственная фича, которая закрывает измеренную дыру продукта: 17 профилей сегодня получают пустой ответ, и по всем 33 критичным навыкам ментор находится.

### Что уже есть в репозитории

- Данные полностью поддерживают механику: employees.skills, role_profiles.critical_skills, department, role, manager_id, история участия в менторских событиях EV_007 и EV_037
- Чистые функции движка, из которых берутся критичные разрывы: analyzeGaps
- Кода механики нет - пишется с нуля

### Как сделать

**Шаг 1. Вход и отбор**

- Вход: employeeId и skillId критичного разрыва (берётся из analyzeGaps)
- Кандидаты: сотрудники с уровнем этого навыка не ниже требуемого для целевого грейда
- Исключить самого сотрудника и его прямого руководителя брать с пониженным приоритетом: разговор с руководителем и так происходит

**Шаг 2. Ранжирование минимум по трём факторам**

- Уровень навыка: выше - лучше
- Близость: тот же департамент или та же роль. До такого человека реально дойти
- Готовность менторить: участие в менторских событиях EV_007 / EV_037 в истории
- Нагрузка: не назначать одного ментора всем подряд. Тот же принцип разнообразия, что уже применён в топ-3 рекомендаций
- Стабильный tie-break по employee_id - как и везде в проекте

**Шаг 3. Приватность - это требование ТЗ, а не пожелание**

- Показываем: имя, роль, грейд, уровень нужного навыка
- Не показываем: историю участия ментора, его вовлечённость, его собственные разрывы
- В ограничениях ТЗ прямо сказано: данные о вовлечённости не видны другим сотрудникам без согласия

**Шаг 4. Где показать**

- В карточке рекомендации как альтернатива: 'курса нет, но есть трое коллег'
- На экране сотрудника в состоянии 'ничего не подходит' - вместо пустоты
- На экране HR: список навыков, которые каталог не закрывает, с указанием, кем их можно закрыть

### Чего не делать

- Не превращать это в рейтинг сотрудников: список менторов - не таблица лидеров, порядок не публичный
- Не копировать логику скоринга активностей - у ментора свои факторы
- Не показывать ментора, если разрыв закрывается обычной активностью: это альтернатива, а не замена
- Не трогать движок рекомендаций и контракты

### Критерии приёмки

| Проверка | Ожидаемый результат |
|---|---|
| Сотрудник без подходящих активностей | Видит менторов вместо пустого экрана |
| Критичный разрыв любой из 33 позиций | Ментор находится |
| Нет ни одного носителя уровня | Честное сообщение, не выдуманный кандидат |
| Ментор показан | Видны только имя, роль, грейд, уровень навыка |
| Одинаковые кандидаты | Стабильный порядок при повторном вызове |
| Один и тот же человек подходит многим | Не оказывается первым у всех подряд |

### Обязательные тесты

- для критичного разрыва возвращается непустой список менторов
- сам сотрудник никогда не попадает в свой список
- при отсутствии носителей возвращается пустой результат без ошибки
- результат детерминирован при одинаковом входе
- в выдаче нет полей истории и вовлечённости
- распределение нагрузки: один ментор не занимает первое место у всех

## 3. Кто выпадает из развития

**Список людей, которые формально участвуют, но срываются - чтобы HR поговорил, а не прислал ещё одно уведомление.**

- Владелец: Даник / поток C
- Каталоги: `src/domain/analytics/**; src/components/hr/**; tests/evaluation/**`
- Оценка: около 40 минут

### Что это простыми словами

Человек числится в программах развития, но раз за разом не доходит: не приходит на сессию, бросает на середине, отказывается от назначенного. Формально он в системе, фактически - выпал.

Экран показывает таких людей и, главное, объясняет причину словами, а не процентом.

### Зачем это нужно

- Это прямое требование кейса к HR-экрану: 'видит, какие компетенции проседают и кто выпадает из развития'. Пункт легко пропустить, а он в обязательной части.
- Данных достаточно: у 81 человека из 200 три и более срыва.
- В ограничениях ТЗ сказано, что принуждение - главный предиктор провала таких программ. Значит смысл экрана - повод для разговора, а не список на наказание. Формулировки должны это отражать.

> Самая дешёвая из четырёх и при этом обязательная: формулировка 'кто выпадает из развития' взята из требований кейса дословно.

### Что уже есть в репозитории

- src/domain/analytics/selectors.ts - агрегаты по истории уже считаются
- src/components/hr/HRDashboard.tsx - есть куда встроить блок
- Разбор статусов и assigned_by описан в docs/DATASET.md

### Как сделать

**Шаг 1. Что считать**

- Срывы за последние 6-12 месяцев: no_show, dropped, declined
- Отдельно - добровольное и назначенное. Это ключевой момент: сорвать то, что выбрал сам - потеря интереса; отказаться от навешенного HR - нормальная человеческая реакция. Смешивать нельзя, это разные диагнозы
- Динамика: стало хуже или лучше по сравнению с предыдущим периодом
- overdue не смешивать с добровольным поведением: это контекст обязательных активностей

**Шаг 2. Что показывать**

- Не число, а фразу с причиной: '4 из 5 назначенных HR активностей не завершены, при этом 2 из 2 выбранных самостоятельно завершены. Проблема не в человеке, а в назначениях'
- Рядом - действие для HR: сменить формат, обсудить с руководителем, снять назначение

**Шаг 3. Чего категорически не делать**

- Не писать 'риск оттока 73%'. Подтвердить это нечем: размеченных данных об увольнениях у нас нет. За выдуманную метрику снимут больше, чем дадут за красоту
- Не делать из этого публичный список: он виден только HR
- Не считать признаком молчание: за последний год хотя бы одну активность завершили все 200 человек, так что 'молчун' в этих данных не существует

### Чего не делать

- Не называть метрику accuracy или вероятностью без размеченных данных
- Не показывать список сотрудникам
- Не менять скоринг рекомендаций

### Критерии приёмки

| Проверка | Ожидаемый результат |
|---|---|
| Агрегаты | Совпадают с прямым подсчётом строк датасета |
| Человек срывает только назначенное | Формулировка указывает на назначения, а не на человека |
| Человек срывает своё | Формулировка указывает на потерю интереса |
| Нет негативной истории | В список не попадает |
| Доступ | Экран виден только роли HR |
| Метрики | Нигде не заявлена вероятность или accuracy |

### Обязательные тесты

- подсчёт срывов совпадает с прямым перебором CSV
- добровольные и назначенные срывы разделены
- сотрудник без негативной истории не попадает в список
- формулировка причины меняется в зависимости от паттерна
- в выдаче нет вероятностных метрик

### Готовое задание для Codex

```
Добавь в HR Command Center блок 'кто выпадает из развития'. Работай только в разрешённых каталогах. Сначала прочитай docs/DATASET.md, раздел про статусы истории и assigned_by. Считай детерминированно, без всякого ML: срывы no_show, dropped и declined за последние 6-12 месяцев, ОТДЕЛЬНО для добровольных активностей (assigned_by=self) и для назначенных (manager, hr), плюс динамику относительно предыдущего периода. Статус overdue не смешивай с добровольным поведением. На выходе - не число, а фраза с причиной и предлагаемое действие для HR. Категорически запрещено: любые вероятности, 'риск оттока', accuracy и прочие метрики, которые нечем подтвердить, - размеченных данных об увольнениях нет. Список виден только HR, публичного рейтинга сотрудников быть не должно. Минимум 5 тестов, включая совпадение агрегатов с прямым подсчётом строк датасета и разделение добровольных и назначенных срывов. В конце запусти pnpm test и pnpm build и перечисли изменённые файлы.
```

## 4. Казахский и русский интерфейс

**Интерфейс и объяснения на языке сотрудника.**

- Владелец: один человек целиком
- Каталоги: `src/lib/i18n/**; строки в компонентах - по согласованию, одним проходом`
- Оценка: около 1 часа

### Что это простыми словами

У каждого сотрудника в данных есть поле preferred_language. Интерфейс и объяснение показываются на его языке, плюс есть ручной переключатель.

### Зачем это нужно

- Из 200 человек 100 предпочитают русский, 89 - казахский, 11 - английский. Это 94% базы.
- Демо-профиль E0028 - казахскоязычный. На защите это увидят сразу, в первом же сценарии.
- Пункт есть в списке необязательных возможностей ТЗ: качественная локализация интерфейса на казахский и русский.
- Стоит дёшево, а выглядит как зрелость продукта.

> Делать последней и одним человеком: правка задевает почти каждый компонент, поэтому параллельно с другими фичами она даст конфликты в каждом файле.

### Что уже есть в репозитории

- src/lib/evaluation/explanations.ts - шаблоны фактов уже на трёх языках ru/kk/en
- Поле preferred_language есть у всех 200 сотрудников
- Единого словаря интерфейсных строк нет - его и надо сделать

### Как сделать

**Шаг 1. Словарь**

- src/lib/i18n/{kk,ru,en}.ts - плоские словари строк и функция подстановки
- Никаких тяжёлых библиотек: 5 часов, задача узкая

**Шаг 2. Выбор языка**

- По умолчанию - preferred_language выбранного сотрудника
- Переключатель в шапке перекрывает автоматический выбор
- Выбор не влияет на расчёты: язык - это только отображение

**Шаг 3. Честная граница**

- В стартовом ките переводов НЕТ, вопреки обещанию в ТЗ организаторов: названия навыков и активностей только на английском
- Значит переводим интерфейс и объяснения, а контент датасета оставляем как есть
- Это ограничение надо явно назвать в README: честная граница лучше, чем видимость полного перевода

### Чего не делать

- Не переводить идентификаторы и названия из датасета - они часть данных
- Не разносить строки по трём веткам одновременно: правка затрагивает почти каждый компонент, делать одним проходом и одним человеком
- Не браться за это раньше, чем закрыты фичи 1-3

### Критерии приёмки

| Проверка | Ожидаемый результат |
|---|---|
| Открыт сотрудник с preferred_language kk | Интерфейс и объяснение на казахском |
| Переключение языка вручную | Меняется отображение, не меняются числа |
| Строка без перевода | Показывается английский вариант, а не пустота и не ключ |
| README | Явно сказано, что контент датасета не переведён |

### Обязательные тесты

- выбор языка берётся из preferred_language сотрудника
- ручной переключатель перекрывает автоматический выбор
- отсутствующий ключ даёт английский fallback, а не пустую строку
- смена языка не меняет результат рекомендации

## Общие правила для всех четырёх заданий

- Перед стартом прочитать AGENTS.md, docs/ARCHITECTURE.md, docs/CONTRACTS.md и docs/DATASET.md.
- Snapshot date датасета - 2026-10-01. new Date() в доменной логике запрещён.
- Доменные функции чистые и детерминированные: одинаковый вход - одинаковый выход, стабильный tie-break.
- Модель никогда не получает сырые профили, историю и текстовые описания из датасета.
- Приложение обязано полностью работать без LLM_API_KEY. Это release gate, его проверяет жюри.
- Публичных рейтингов сотрудников нет ни в одной из фич - прямой запрет ТЗ.
- Уровни навыков всегда 0..5, факторы score всегда 0..1.
- Не менять файлы вне разрешённых каталогов. Нужен чужой файл - сказать об этом в ответе.
- Не предлагать новых возможностей после выполнения P0.

## Чего не делаем вообще

- Внутренняя валюта, магазин наград, бейджи - геймификация прямо названа в ТЗ надстройкой вне обязательной части.
- Публичный рейтинг сотрудников по результативности - прямой запрет.
- Очки за обязательные процессы - прямой запрет.
- ML-прогноз оттока - нечем подтвердить, размеченных данных нет.
- OAuth, SQL-база, интеграция с мессенджером - вне пятичасового релиза.

# Evaluation — как мы доказываем качество

> **Правило: не называть метрику `accuracy`, пока нет размеченных правильных рекомендаций.**
> Жюри это заметит, а честная формулировка стоит дороже красивой цифры.

> **Текущий этап:** интеграция Skill Exchange с PR #10 (внешнее обучение) и
> PR #11 (профили жюри) из `main f287b406`. Результаты прежних версий ниже
> обозначены отдельно; итог объединения — 268/268 тестов в 32 файлах и production
> build с полной проверкой TypeScript, PASS.

## 1. Baseline, с которым сравниваемся

**Weakest-skill baseline** — «рекомендуй активность, развивающую самый низкий навык сотрудника».
Это тот самый однофакторный подход, который ТЗ организаторов прямо запрещает выдавать за AI.
Мы реализуем его честно, чтобы показать разницу на конкретном профиле.

## 2. Метрики

| Метрика | Определение | Цель |
|---|---|---|
| Eligibility violations | доля рекомендаций, нарушивших хотя бы один hard filter | **0** |
| Evidence Receipt completeness | доля рекомендаций с target, gap, gain, history, feasibility и projection evidence | **100%** |
| LLM output boundary | `/api/ai/review`: только candidate/evidence IDs; `/api/ai/explain`: проверяемое объяснение относительно ограниченного evidence | неизвестные ID/числа и неподтверждённые утверждения блокируются |
| History replay correctness | совпадение effective skills с эталонным пересчётом | **100%** |
| Critical-gap targeting | доля рекомендаций, закрывающих критичный для промоушена навык | выше baseline |
| Abstain honesty | доля профилей без кандидатов, где система честно молчит, а не выдумывает | **100%** |
| Latency p50 / p95 | время отклика рекомендации | ≤ 10 с (требование ТЗ) |
| Fallback status | поведение без LLM-ключа | полностью рабочее |

## 5. Проверенные пробелы каталога

На snapshot **2026-10-01** у **125 из 200 сотрудников** есть хотя бы один открытый
критичный разрыв, для которого **нет доступной сейчас активности с положительным
effective gain** по этому навыку. Это **188 пар «сотрудник — критичный навык»**.
Для любых открытых разрывов, включая некритичные, таких сотрудников **184**, а не 183.

Методика: для каждого профиля получить effective skills после replay и целевой набор
требований; взять gaps с `gap > 0`; проверить все добровольные события через
`evaluateEligibility`. Разрыв относится к этой метрике, если ни у одного допустимого
события нет `effectiveGains[skillId] > 0`. Затем отдельно подсчитать уникальных сотрудников
с критичными разрывами и сами пары. Профили без цели не добавляют gaps в этот подсчёт.

Метрика относится к **текущему доступному шагу**. Она не означает, что разрыв невозможно
закрыть цепочкой шагов, что никакая активность не развивает навык или что повышение
гарантированно заблокировано навсегда. Именно для таких случаев предлагаются наставники
и внешнее обучение.

## 7. Известные ограничения текущей реализации

- Сервер проверяет подписанную demo identity, но синтетическую persona можно свободно
  выбрать. Для реальных данных нужны SSO/RBAC и audit log.
- Demo Employee получает только собственный профиль/историю; HR — полный bundled dataset.
  Чужая переписка HR доступна только как агрегаты.
- Карьерный ledger и judge import живут в памяти вкладки; reload сбрасывает их.
  Server JSON чата сохраняется отдельно. IndexedDB не подключён к активному UI.
- `/api/ai/explain` поддерживает browser import и проверяет ответ относительно присланных
  фактов; происхождение этих фактов сервером не подтверждается. IDs-only `/api/ai/review`
  использует bundled dataset и доступен к собственному профилю либо HR.
- Live внешний LLM не вызывался; success/no-key/outage/timeout/verifier проверяются
  mock transport и локальным fallback. Это не измерение качества произвольных ответов модели.
- Короткий/пустой путь допустим: отсутствие текущей активности явно показывается;
  предложение наставника или внешнего обучения не меняет детерминированный ranking A.

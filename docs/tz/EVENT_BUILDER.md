# Конструктор событий для HR

**Создание активностей, дедлайны и экспорт в календарь**

_ТЗ для Codex - приоритет 2_

> Самое выгодное соотношение эффекта к цене из всего списка. Полтора часа работы превращают HR-экран из констатации проблемы в инструмент её решения - прямо на глазах у жюри.

## 1. Зачем это нужно

Измерено на реальных данных: каталог компании не закрывает 59 навыков из 60. Leadership блокирует повышение 34 людям, Mentoring - 19. Всего 125 человек имеют критичный разрыв, которому не соответствует ни одна активность в каталоге.

Сейчас HR-экран это показывает - и на этом всё. Констатация без действия.

> **Конструктор замыкает цикл прямо на демо: HR видит «Leadership - блокер у 34 человек, в каталоге нечем» → нажимает «создать активность» → заполняет форму → рекомендации у этих 34 пересчитываются на глазах. Это самый сильный HR-момент из всех возможных, и он стоит полтора часа.**

Важное отличие от внешних курсов: событие, созданное HR, имеет настоящие gain и max_level, заданные человеком, который отвечает за программу. Поэтому оно честно участвует в скоринге, тогда как внешний курс остаётся вне расчётов.

## 2. Создание события

Форма заполняет ровно ту же структуру, что и events.json, и проходит ту же Zod-схему. Никакой параллельной модели данных.

| Поле | Правило валидации |
|---|---|
| event_id | Генерируется с префиксом EV_HR_, проверяется на коллизии |
| title, description | Обязательны, непустые |
| type | Из значений, которые уже встречаются в каталоге |
| format | online, offline или self_paced |
| duration_hours | Больше нуля |
| mandatory | Принудительно false, поле недоступно для редактирования |
| target_roles, target_grades | Выбор из значений, существующих в данных |
| develops_skills | Только существующие skill_id; gain от 1 до 2; max_level не выше 5 |
| prerequisites | Только существующие skill_id, уровень от 0 до 5 |
| upcoming_sessions | Для online и offline - хотя бы одна дата не раньше 2026-10-01; для self_paced список пуст |
| enrollment_deadline | Необязательно. Не раньше snapshot date и не позже первой сессии |

> **Поле mandatory заблокировано намеренно. Обязательные события исключены из рекомендаций правилами домена, а механика вокруг обязательных процессов прямо запрещена ТЗ. Возможность создать обязательное событие была бы и бесполезной, и нарушающей условия.**

## 3. Предпросмотр эффекта - ключевая часть

До сохранения система прогоняет проверку допустимости по всем 200 сотрудникам существующими чистыми функциями и показывает результат.

```
Предпросмотр: Leadership Practicum for Middle

  станет доступна:                 41 сотруднику
  закроет критичный разрыв:        34 сотрудникам
  навыков перестанет быть непокрытыми: 1  (SK_LEADERSHIP)
  из 125 человек с непокрытым критичным разрывом останется: 91
```

Ничего нового считать не нужно: используются evaluateEligibility и analyzeGaps. Предпросмотр обязан совпадать с фактическим результатом после сохранения - это отдельный тест.

## 4. Дедлайны

- enrollment_deadline - необязательная дата окончания записи.
- Ограничения: не раньше snapshot date, не позже первой сессии.
- Во всех расчётах «осталось N дней» используется snapshot date 2026-10-01, а не системные часы. new Date() в доменной логике запрещён - иначе ломаются тесты и воспроизводимость.
- Сотруднику дедлайн показывается на карточке рекомендации.
- Дедлайн не влияет на скоринг: это информация, а не фактор ранжирования.

## 5. Хранение и честная граница

- Созданные события живут в сессии, рядом с журналом выполнения.
- В data/source ничего не пишется: это данные организаторов, они неприкосновенны.
- Повторный импорт сбрасывает созданные события.
- В интерфейсе они помечены как созданные HR.
- Ограничение описывается в README - той же формулировкой, что и про журнал прогресса: в продакшене заменяется хранилищем без изменения движка.

## 6. Календарь

Пункт «встраивание в календарь» из необязательного списка ТЗ закрывается генерацией .ics - это обычный текстовый файл. Ни одного обращения к сети, работает офлайн, не добавляет точек отказа на демо.

### Требования формата RFC 5545

- Переводы строк CRLF.
- Уникальный UID на каждое событие.
- Обязательные DTSTAMP и PRODID.
- Сворачивание длинных строк.
- Экранирование запятых, точек с запятой и переводов строк в текстовых полях.
- Кодировка UTF-8.

### Две точки экспорта

| Что экспортируем | Содержимое |
|---|---|
| Одна активность | Все её будущие сессии, название, описание, длительность |
| Личный план сотрудника | Шаги принятой траектории и ближайшие сессии рекомендованных активностей |

Плюс кнопка «добавить в календарь» на карточке рекомендации - самое естественное место.

## 7. Порядок реализации

| Фаза | Что делаем | Оценка |
|---|---|---|
| 1 | Форма, валидация, добавление в каталог сессии | 40 мин |
| 2 | Предпросмотр эффекта | 30 мин |
| 3 | Экспорт .ics для активности | 20 мин |
| 4 | Дедлайны в интерфейсе и .ics для личного плана | 30 мин |

## 8. Критерии приёмки

| Проверка | Ожидаемый результат |
|---|---|
| Событие с несуществующим skill_id | Отклонено схемой с указанием поля |
| Формат online без будущей сессии | Отклонено |
| Попытка выставить mandatory в true | Невозможна в интерфейсе и отклоняется схемой |
| gain больше 2 или max_level больше 5 | Отклонено |
| Дедлайн позже первой сессии | Отклонено |
| Предпросмотр показал 34 человека | После сохранения затронуто ровно 34 |
| Сохранение события | Рекомендации затронутых сотрудников пересчитаны |
| HR-экран после сохранения | Навык ушёл из списка непокрытых |
| Экспорт .ics | Файл открывается календарём, даты и экранирование корректны |
| Повторный импорт набора | Созданные HR события сброшены, об этом сказано |

## 9. Обязательные тесты

- событие с несуществующим skill_id отклонено;
- scheduled-событие без будущей сессии отклонено;
- mandatory нельзя выставить в true ни через форму, ни напрямую;
- предпросмотр совпадает с фактическим числом затронутых после сохранения;
- новое событие появляется в рекомендациях у затронутых сотрудников;
- навык уходит из списка непокрытых на HR-экране;
- файл .ics содержит CRLF, уникальные UID и корректное экранирование;
- расчёт оставшихся дней использует snapshot date, а не системные часы.

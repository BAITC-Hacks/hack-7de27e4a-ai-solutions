# Экономика развития

**Валюта, признание, каталог вознаграждений и личные вызовы**

_ТЗ для Codex - геймификация_

> Геймификация, которая что-то решает: баллы оплачивают внешние курсы тем 88 сотрудникам, чей блокер повышения каталог компании закрыть не может. Не фантики, а механизм распределения бюджета на развитие.

## 1. Зачем и главный принцип

Геймификация стоит в названии кейса, но ТЗ прямо говорит: это надстройка, в обязательную часть она не входит, а ядро задачи - качество и объяснимость рекомендации. Значит геймификация обязана быть не украшением, а работающим механизмом, иначе она отнимает время у того, что оценивается.

> **Баллы ради баллов жюри не купит. Но у нас измерена дыра: 88 человек имеют технический блокер повышения, которому в каталоге компании не соответствует ни одна активность. Их лечит внешний курс, а курс стоит денег. Отсюда смысл валюты: сотрудник зарабатывает баллы развития и тратит их на то, что реально ускоряет карьеру - в первую очередь на внешний курс, который компания иначе не купила бы.**

Так валюта становится механизмом распределения того самого бюджета на развитие, который по условию задачи «расходуется полностью при низкой явке». Это прямое попадание в формулировку проблемы из ТЗ.

## 2. Рамки, заданные ТЗ

| Запрет из ТЗ | Что из этого следует |
|---|---|
| Публичные рейтинги сотрудников по результативности | Нет лидерборда, нет сортировки людей по баллам, чужой баланс не виден никому |
| Механика вокруг обязательных процессов | За обязательные события - ноль баллов. Отдельный тест |

## 3. Архитектура

### Принцип: производное, а не хранимое

Центральное решение, от которого зависит всё остальное: баланс НЕ хранится. Он вычисляется.

```
balance = earned - spent

earned  = чистая функция(датасет, журнал выполнения, правила v1)
spent   = сумма хранимых списаний
```

Что это даёт: повторный импорт того же набора даёт тот же баланс; дрейфа состояния не существует в принципе; всё покрывается модульными тестами без интерфейса; начисление всегда можно объяснить, потому что оно выводится из фактов, а не накоплено неизвестно когда.

| Тип состояния | Что сюда входит | Где живёт |
|---|---|---|
| Производное, не хранится | Заработанные баллы, прогресс вызовов, достижения | Вычисляется из датасета и журнала |
| Хранимое, намеренные действия | Списания, принятие вызова, отправленные благодарности, отказ от геймификации | Журнал геймификации рядом с журналом выполнения |

### Поток данных

```
  датасет (200 профилей, история)  --+
  журнал выполнения (ledger)       --+--> earnPoints()  ---> earned
  правила v1 (конфиг)              --+     чистая функция
                                                              |
  списания (хранимые)  ------------------------> spent        |
                                                    |         |
                                          balance = earned - spent
                                                    |
        +-------------------------+-----------------+----------------+
        v                         v                                  v
  баланс и квитанция        каталог наград                    личные вызовы

  движок рекомендаций  <-- СВЯЗИ НЕТ. Ни в одну сторону.
```

> **Изоляция от движка - жёсткое требование, а не пожелание. Геймификация никогда не влияет на рекомендации, ранжирование, readiness и прогресс навыков. Обязателен тест: результат recommendForEmployee побайтово одинаков при пустом и при заполненном состоянии геймификации. Если баллы начнут двигать рекомендации, мы потеряем то самое, на чём держится весь продукт.**

### Правила в версионируемом конфиге

data/gamification_rules.json с полем version - по образцу весов движка. Версия правил показывается в интерфейсе рядом с балансом. Это та же дисциплина, что и версия движка в квитанции рекомендации: пользователь всегда знает, по каким правилам ему начислено.

## 4. Начисление

```
points(активность) = base × critical_multiplier × gap_relevance

  base                = 10        (конфиг)
  critical_multiplier = 2.0, если активность даёт положительный прирост
                        по навыку из critical_skills целевого грейда,
                        иначе 1.0   -- тот же множитель, что в движке
  gap_relevance       = 1.0, если есть прирост по целевому разрыву,
                        иначе 0.5   -- учиться сверх плана тоже ценно, но меньше

  обязательное событие -> 0, без исключений
```

| Начисляем | Не начисляем |
|---|---|
| Завершение добровольной активности | Обязательные события - прямой запрет ТЗ |
| Закрытие критичного разрыва (множитель 2.0) | Вход в систему, присутствие, «активность» |
| Менторская помощь: принятый и закрытый тред | Что-либо, где есть сравнение с другими |
| Полученная благодарность от коллеги | Передача баллов между сотрудниками |
| Завершение личного вызова |  |

Половина начислений - за помощь другим. Именно это превращает Skill Exchange из чата в экономику: у 47 потенциальных менторов появляется причина ответить на запрос.

### Квитанция за баллы

Каждое начисление объяснимо - теми же принципами, что и рекомендация. Неразложимых чисел в продукте не должно быть нигде.

```
Начислено 20
  активность EV_012 завершена 2026-08-14
  развивает SK_SYSTEM_DESIGN, он критичен для Senior Backend Engineer
  базовые 10 × критичный множитель 2.0 × релевантность 1.0
  правила v1
```

## 5. Трата и каталог вознаграждений

data/rewards.json - курируемый каталог. Позиции подобраны так, чтобы трата ускоряла карьеру, а не развлекала.

| Награда | Смысл |
|---|---|
| Оплата внешнего курса | Главная связка: закрывает блокер у тех самых 88 человек |
| Час с Lead по своему критичному навыку | Связка с менторской механикой |
| День на обучение | Время - самый дефицитный ресурс в развитии |
| Билет на конференцию | Понятная и реальная статья бюджета |

Никаких кружек, стикеров и аватарок: они превращают серьёзный инструмент в игрушку и на защите выглядят несолидно.

- Списание создаёт неизменяемую запись журнала с балансом до и после - по образцу журнала выполнения.
- Повторное списание защищено от двойного применения.
- Баланс никогда не уходит в минус.
- Передача баллов между сотрудниками НЕ реализуется: она создаёт рынок, накрутку и скрытое сравнение.

## 6. Признание от коллег

- Благодарность отправляет только вторая сторона завершённого менторского треда.
- Не более одной благодарности на тред.
- Себе - невозможно.
- Действует потолок засчитываемых благодарностей за период, значение из конфига.
- Если Skill Exchange ещё не реализован, модуль работает без него: менторские начисления равны нулю и ничего не падает.

## 7. Личные вызовы

- Предложения выводятся из разрывов: закрыть критичный разрыв; завершить N добровольных активностей; помочь коллеге один раз.
- Принятие вызова хранится, выполнение вычисляется из тех же фактов.
- Срок считается ОТ snapshot date 2026-10-01, не от системных часов.
- Провал не отнимает ничего и не окрашивается негативно: «не получилось» - нейтральное состояние, а не потеря. Это прямое следствие требования добровольности.

## 8. Приватность и антипаттерны - структурно

> **Эти правила должны быть заложены в устройство кода, а не в дисциплину разработчика. Спрятанная кнопка - не защита.**

| Правило | Как обеспечивается |
|---|---|
| Чужой баланс не виден никому | Нет ни одного метода, возвращающего чужой баланс |
| Нет рейтингов | Нет ни одного экрана с сортировкой людей по баллам |
| HR не видит персональных баллов | HR-срез принимает только агрегаты |
| Отказ от геймификации | Скрывает её полностью и исключает из агрегатов |
| Командные механики | Не реализуются: рейтинг отделов - тот же лидерборд в профиль |

### Что видит HR

Только агрегаты: сколько баллов выдано всего, распределение трат по категориям, доля участвующих. Без единой привязки к конкретному человеку. Это же и полезнее: HR нужен сигнал о том, работает ли программа, а не список отличников.

## 9. Порядок реализации

| Фаза | Что делаем | Что работает по итогу | Оценка |
|---|---|---|---|
| 1 | Конфиг правил, чистая функция начисления, квитанция, тесты | Баланс считается и объясняется, интерфейса ещё нет | 1 ч |
| 2 | Журнал списаний, каталог наград, обмен | Баллы можно потратить | 1 ч |
| 3 | Личные вызовы | Принятие и выполнение | 40 мин |
| 4 | Признание от коллег | Работает при наличии Skill Exchange | 30 мин |
| 5 | Агрегаты для HR и отказ от геймификации | Приватность и добровольность закрыты | 30 мин |

Итого около 3.5 часов. Фаза 1 самодостаточна: даже без интерфейса она даёт проверяемую тестами экономику.

## 10. Критерии приёмки

| Проверка | Ожидаемый результат |
|---|---|
| Завершено обязательное событие | Начислено ноль баллов |
| Активность закрывает критичный разрыв | Применён множитель 2.0, видно в квитанции |
| Состояние геймификации меняется | Рекомендации не меняются вообще |
| Повторный импорт того же набора | Тот же баланс |
| Запрос чужого баланса | Такого метода не существует |
| Повторное нажатие «получить награду» | Списание применено один раз |
| Награда дороже баланса | Списание отклонено, баланс не в минусе |
| Благодарность самому себе | Невозможна |
| Skill Exchange не реализован | Модуль работает, менторские начисления равны нулю |
| Срок вызова | Считается от snapshot date, а не от системных часов |
| Отказ от геймификации | Интерфейс скрыт, сотрудник исключён из агрегатов HR |
| HR-экран | Только агрегаты, ни одного имени рядом с баллами |

## 11. Обязательные тесты

- обязательное событие даёт ноль баллов;
- критичный навык даёт множитель 2.0;
- активность вне целевых разрывов даёт коэффициент 0.5;
- рекомендации побайтово одинаковы при пустом и заполненном состоянии геймификации;
- повторный импорт воспроизводит баланс;
- квитанция раскладывает начисление на факты;
- повторное списание не применяется дважды;
- баланс не уходит в минус;
- благодарность себе невозможна, на тред засчитывается одна;
- срок вызова считается от snapshot date;
- модуль работает без Skill Exchange;
- в публичном API отсутствует метод получения чужого баланса.

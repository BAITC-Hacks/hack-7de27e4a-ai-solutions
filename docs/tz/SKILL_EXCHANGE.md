# Skill Exchange

**Поиск коллег по навыкам и менторская переписка**

_ТЗ на продвинутую фичу - 1 из 2_

> Развитие через людей, а не только через каталог. Документ описывает, зачем это нужно по данным, где проходит граница реализуемого за время хакатона и как собрать это, не сломав ни один release gate.

> **Принятые допущения, потому что решение по ним не поступало: хранилище - JSON-файл (переживает перезапуск, ноль зависимостей); мессенджер делаем полный, а не урезанный; порядок относительно агентного слоя не зафиксирован - если времени хватит только на одно, агент выгоднее по разбалловке. Любое из трёх меняется одной строкой в этом документе.**

## 1. Зачем это нужно

Идея пришла от команды, но данные её подтверждают жёстче, чем ожидалось. Все цифры ниже посчитаны скриптом на реальном data/source.

| Что померили | Значение |
|---|---|
| Сотрудников, у которых есть карьерная цель | 190 из 200 |
| У скольких хотя бы один разрыв, который каталог компании закрыть НЕ может | 183 |
| У скольких непокрытый разрыв является КРИТИЧНЫМ, то есть блокирует повышение | 125 |
| Различных навыков, которые каталог не закрывает | 59 из 60 |
| Профилей, где после hard-фильтров нет вообще ни одной рекомендации | 17 |
| Менторских событий в каталоге | 2 из 40 |
| Критичных навыков, по которым в компании есть носитель уровня 4+ | 33 из 33 |

> **125 человек не могут получить повышение, и каталог компании им ничем не поможет. При этом в 188 таких случаях нужный уровень навыка уже есть у кого-то внутри компании. Ресурс существует - он просто не связан с теми, кому нужен.**

### Почему именно ментор, а не курс

Разложил 125 человек по типу непокрытого критичного навыка:

| Тип непокрытого критичного разрыва | Человек | Чем лечится |
|---|---|---|
| Только soft-навыки | 37 | ментор |
| И soft, и hard | 10 | ментор плюс курс |
| Только hard-навыки | 78 | внешний курс, см. второе ТЗ |

Топ непокрытых критичных навыков: Leadership у 34 человек и Mentoring у 19. Это пятьдесят три человека, чей блокер повышения - навык, которому в принципе не учат курсом. Его перенимают, работая рядом с тем, кто умеет. Именно это и делает менторский поиск не украшением, а закрытием измеренной дыры продукта.

## 2. Что входит и что не входит

Слово «мессенджер» скрывает большой разброс по стоимости. Фиксирую границу явно.

### Входит - работает по-настоящему

- Переписка хранится на сервере: переживает перезагрузку страницы и перезапуск приложения.
- Два человека в двух окнах браузера реально обмениваются сообщениями.
- Список диалогов, непрочитанные, тема запроса, статусы принят/отклонён/закрыт.
- Поиск коллег по навыку с фильтрами по отделу, роли и доступности.
- Разграничение доступа сотрудник/HR - причём это невыполненный пункт обязательной части ТЗ.
- Переключатель «доступен для менторства» - механизм согласия, которого требует ТЗ.

### Не входит - и это надо сказать в README

- Настоящей аутентификации нет. Вход - выбор сотрудника, сервер ставит подписанную куку. Это идентичность для демо, не безопасность. В проде заменяется SSO.
- Нет пуш-уведомлений, вложений, редактирования и удаления сообщений, шифрования.
- Нет WebSockets - см. раздел 3, это осознанный технический отказ.
- Нет базы данных и OAuth - оба вынесены за скоуп на старте проекта, и это решение не пересматривается.

> **Слой идентичности - не накладные расходы на чат. Обязательные требования кейса включают разграничение прав сотрудник/HR и приватность данных о вовлечённости. Сейчас этого нет вообще: любой видит всё. Чат садится на слой, который надо было делать в любом случае.**

## 3. Архитектура: пять слоёв

| Слой | Решение | Почему так |
|---|---|---|
| Идентичность | httpOnly SameSite=Lax кука с подписанным employee_id | Без OAuth. Даёт «кто я» для чата и разграничение прав для ТЗ |
| Хранилище | JSON-файл data/runtime/messages.json плюс кэш в памяти | Переживает перезапуск, ноль зависимостей. SQLite тянет нативный модуль и риск сборки Docker; Postgres вне скоупа; память процесса теряет переписку при перезапуске |
| API | Обычные route handlers Next.js | Ровно та же механика, что у уже работающего /api/ai/review |
| Живое обновление | Опрос раз в 3 секунды, пока вкладка видима | Работает везде: в контейнере, за прокси, в любом браузере. SSE - опциональный апгрейд |
| Интерфейс | Страница /chat: входящие, тред, поиск коллег | Две точки входа: из результата поиска и из навигации |

> **WebSockets не используем. App Router не поддерживает их в маршрутах, нужен кастомный сервер, а он ломает next start и standalone-сборку в Docker. То есть ради незаметной на демо разницы мы бы уронили release gate «запуск одной командой». Опрос раз в три секунды выглядит так же.**

### Замечание по Docker

В standalone-образе приложение работает от непривилегированного пользователя. Каталог data/runtime должен существовать и быть доступен ему на запись - это правится в Dockerfile при сборке образа. Если каталог недоступен, приложение обязано подняться и работать без чата, а не упасть.

## 4. Модель данных

Описание, а не код: конкретные типы владелец оформляет сам и согласует до начала работы.

```
Thread
  id, skillId, requesterId, mentorId, subject
  status: open | accepted | declined | closed
  createdAt, lastMessageAt

Message
  id, threadId, authorId, text (plain text, max 2000), sentAt, readBy[]

MentorAvailability
  employeeId, available: boolean, updatedAt
  по умолчанию выводится из участия в EV_007 / EV_037

Session (кука)
  employeeId, issuedAt, подпись
```

### Поиск: что на входе и что на выходе

- Вход: employeeId просящего, skillId критичного разрыва, необязательные фильтры по отделу и роли.
- Кандидаты: effective-уровень навыка не ниже требуемого для целевого грейда просящего. Именно effective, после replay истории - иначе ментор с устаревшим профилем не найдётся.
- Ранжирование минимум по четырём факторам: уровень, близость по отделу и роли, проявленная готовность менторить, распределение нагрузки.
- Выдаётся только: имя, роль, грейд, уровень запрошенного навыка, признак доступности.

### Поверхность API

| Маршрут | Назначение |
|---|---|
| POST /api/identity/session | Демо-вход: принимает employeeId, ставит подписанную куку |
| GET /api/identity/session | Кто я сейчас и какая у меня прикладная роль |
| DELETE /api/identity/session | Выход |
| GET /api/messages/threads | Мои диалоги со счётчиком непрочитанных |
| POST /api/messages/threads | Создать запрос: skillId, тема, первое сообщение |
| GET /api/messages/threads/{id} | История треда, только для участников |
| POST /api/messages/threads/{id} | Отправить сообщение |
| POST /api/messages/threads/{id}/read | Отметить прочитанным |
| GET /api/messages/updates | Инкрементальная выборка по курсору - для опроса |
| PUT /api/mentorship/availability | Переключатель доступности, только свой |
| GET /api/mentorship/search | Поиск коллег по навыку с фильтрами |

## 5. Приватность и доступ

> **Это не пожелание, а два прямых ограничения ТЗ организаторов: разграничение прав сотрудник/HR и «данные о вовлечённости не видны другим сотрудникам без согласия». Проверки делаются на сервере. Скрыть кнопку в интерфейсе - не защита.**

| Правило | Как проверяется |
|---|---|
| Тред читают только его участники | Сервер сверяет employeeId из куки с requesterId и mentorId |
| HR не читает чужую переписку вообще | HR-поверхность получает только счётчики и агрегаты |
| Уровень навыка коллеги показывать можно | Это не данные о вовлечённости |
| История участия ментора не показывается никогда | Её нет в модели ответа поиска в принципе |
| Доступность меняет только владелец | Сервер игнорирует чужой employeeId в запросе |
| Текст сообщений - данные, не разметка | Хранится и выводится как обычный текст, без HTML |

## 6. Порядок реализации

Пять фаз. Каждая самодостаточна: обрыв на любой границе оставляет работающий продукт, а не половину функции.

| Фаза | Что делаем | Что работает по итогу | Оценка |
|---|---|---|---|
| 1 | Поиск коллег, чистый модуль без сервера | Пустой экран у 17 профилей заменяется списком коллег. Ценность есть уже здесь | 1 ч |
| 2 | Идентичность и разграничение прав | Закрыт невыполненный пункт обязательной части ТЗ | 1-1.5 ч |
| 3 | Хранилище и API, входящие | Заявку можно отправить и увидеть у ментора | 1-1.5 ч |
| 4 | Тред, отправка, опрос | Полноценная переписка в двух окнах | 2-3 ч |
| 5 | Доступность, лимиты, деградация | Согласие, защита от спама, чат не валит приложение | 1 ч |

Итого 6-8 часов работы через Codex. Если времени меньше - останавливаться после фазы 2 или 3, а не пытаться сжать все пять.

## 7. Критерии приёмки

| Проверка | Ожидаемый результат |
|---|---|
| Профиль без подходящих активностей | Видит список коллег вместо пустого экрана |
| Любой из 33 критичных навыков | Ментор находится |
| Ментор с активностью после last_review_date | Уровень учитывает replay, а не сырой профиль |
| Повторный вызов поиска | Тот же порядок кандидатов |
| Один коллега подходит многим | Не оказывается первым у всех подряд |
| Два окна, два сотрудника | Сообщения долетают в обе стороны в пределах трёх секунд |
| Перезагрузка страницы | Переписка на месте |
| Перезапуск приложения | Переписка на месте |
| Попытка открыть чужой тред | Отказ на сервере, не скрытая кнопка |
| Вход под HR | Чужая переписка недоступна, видны только агрегаты |
| В карточке коллеги | Нет истории участия и вовлечённости |
| Хранилище недоступно | Чат сообщает о недоступности, остальные экраны работают |
| Спам сообщениями | Срабатывает лимит частоты |
| Сообщение с HTML внутри | Отображается как текст |

## 8. Обязательные тесты

- поиск возвращает непустой список для критичного разрыва;
- сам сотрудник никогда не попадает в свой список;
- уровни кандидатов берутся после replay истории;
- результат поиска детерминирован при одинаковом входе;
- нагрузка распределяется: один ментор не первый у всех;
- в ответе поиска отсутствуют поля истории и вовлечённости;
- чтение чужого треда отклоняется на сервере;
- HR не получает содержимое переписки;
- переключатель доступности не меняется от чужого имени;
- лимит частоты сообщений срабатывает;
- недоступное хранилище не роняет остальные маршруты;
- текст сообщения сохраняется и выводится без интерпретации разметки.
